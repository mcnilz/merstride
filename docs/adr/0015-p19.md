# P19 workflow context, short identities and deliberate discard

Supersedes ADR 0014's selection and retention restrictions. Storage discovery,
explicit execution, per-run locking and frozen definitions remain authoritative.

Start always creates a distinct ready run and selects it, both as the state root's
current run and for its `(absolute source path, workflow ID)` pair. Paths are
lexically normalized with native case comparison; symlink aliases are distinct.
Identical workflow IDs in different files remain distinct. Changed source content
does not change the association or the frozen definition. Renamed files are new
associations; use an explicit run ID to continue the original. Missing source files
do not prevent continuation. `--file` is a path selector, never a recompile.

Run selection precedence: explicit run ID or workflow path (positional or --file)
and optional `--workflow`;
remembered current run; exactly one stored run only when no context file exists
(legacy migration). Combining explicit ID with workflow selectors is a usage error.
Multiple workflows at one path require `--workflow`. Missing/stale/corrupt context
fails with guidance, never falls back to another run. Terminal runs remain selected.

The positional workflow spelling matches validate/start: status/advance/complete/
resolve/logs accept [run-id|file]. Bare tokens beginning r_ are reserved for run
IDs, including malformed IDs; every other positional token is a workflow source
path, regardless of extension or existence. `./r_000001` or --file r_000001
unambiguously selects an ID-shaped filename. Native relative/absolute path rules,
quoted spaces and -- literal delimiters apply. Exactly one positional selector OR
--file is allowed; --workflow requires a source path. Invalid path syntax is USAGE
(2), malformed r_ IDs INVALID_RUN_ID (4), absent workflow associations STALE_CONTEXT
(4). This deliberately reinterprets former invalid non-r_ run tokens as paths.
runs [file] filters inventory. use/discard continue to require explicit IDs.
`use <run-id>` deliberately selects a run; ordinary explicit inspection/execution
does not switch context. Context belongs to the resolved state root, shared by
project subdirectories and all callers using that root. Explicit roots are isolated.

Starts/use/discard serialize with an OS-backed root context lock. A competing
context writer fails immediately; retry explicitly. Each invocation resolves one
run before taking its existing writer lock; a subsequent context change cannot
retarget that operation. Simultaneous callers needing independent context should
use `--file` or explicit IDs. Last successfully committed context wins, never an
undocumented newest-state scan. Context writes are atomic. A start that cannot
save context may leave its new ready run; `runs` and `use` recover it explicitly.

Completion always requires a stable request ID. With no run/file selector,
completion locates that request among current requests AND historical receipts
in this root, independent of changing current context. Ambiguous request prefixes
fail. Unreadable states fail closed during this search. Explicit run/file selectors
bound that search. Delayed replies and equivalent historical retries never complete
a newer request. Automation should retain exact runId/request IDs and --state-dir.

New IDs are canonical `r_`/`q_` plus six lowercase hex digits: eight characters
total. They are opaque, predictable identities, not secrets. A durable allocator
and exclusive short-lived identity lock reserve IDs before use. Reservations
survive discard; collisions skip occupied reservations and live run directories.
After 0xffffff allocations the hex part grows, up to sixteen digits; exhaustion
fails without reuse. Crashes may burn IDs. Activations retain random 34-character
IDs because they are secondary log/history selectors, not routine workflow input.

Exact stored run/request IDs win over prefix convenience, including when a longer
new or legacy identity begins with the entire short ID. This deliberately changes
prefix resolution in that case; automation retains exact IDs rather than prefixes.
Existing 34-character run/request IDs, state snapshots, absolute roots and unique
prefixes remain accepted. New selectors accept six or more hex digits. Existing
state has no source association until a new start; `runs`/`use`/explicit IDs remain
available. Protocol 1 JSON keeps its fields and opaque identities; IDs now have
the new canonical length, so clients must not assume a UUID shape. SourcePath,
run inventory and discard result fields are additive. Older binaries do not
understand new short-ID directories or additive state fields: use this binary
for roots that have adopted P19. No automatic state relocation or rewriting.

Retention is explicit: start never deletes anything. `runs [--file ...]` identifies
stored runs and their source/status; `discard <run-id>` removes one deliberately
selected run including logs and receipts, regardless of terminal status. It
refuses a held run lock, unreadable/corrupt state, unexpected files and symlinks/
reparse points. A directory name alone never authorizes deletion. It never kills
processes or reverses external effects. Inspect interrupted effects before discard.

Discard holds the context lock and takes the run lock, validates owned paths,
saves a durable discard marker, and releases the run lock. All new run writers
check that marker under their lock and refuse execution. This allows Windows to
atomically move the directory into this root's `.trash` without open child handles.
Discard clears only references to that run, then
deletes validated files without following links. Readers already holding a snapshot
may finish; new writers cannot enter the moved run. Failure is reported, never
claimed as success; a staged discard is shown by `runs` and can be retried with
the same explicit ID. Authoritative state is deleted last. A minimal ownership
record (run/source/workflow only, no logs or receipts) survives until the empty
stage directory is removed. An interrupted final removal can therefore be retried
by the same ID, including an already empty or already removed stage. Unknown contents are
preserved for investigation. Unrelated workflows and allocator reservations are
never discarded. A cleared context requires start/use; it never selects a survivor.

No P20 output redesign, P21 combined execution, remote storage, dependency change
or release qualification is included. Native CLI scenarios cover this decision.
