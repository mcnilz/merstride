# P20 readable flow progression and results

Supersedes the human layout in ADRs 0010 and 0013. Retain their persistence-linked
observation, escaping, stream roles and JSON suppression. Execution, state schema,
locks, limits, receipt identities and CLI exit codes do not change.

Use compact ASCII lines prefixed with the canonical run ID. Separate process
activation/result from numbered cursor movements and run-status/result changes.
Explain route selection: exact outcome, default because no exact match, or an
unlabeled edge accepting every result including failures. State that the cursor
stays when there is no route. A process result is never the overall run result.
Show visit counts and revisited destinations using the existing bounded activation
array; include no history dump or new event storage. Node IDs are already stable,
short, unique and valid routing names; use them rather than persisting or decoding
Mermaid display labels. Full activation IDs remain available in JSON, selected
logs and secondary text log-selector details, rather than every live sentence.

Accepted completion prints two lines after its save: agent/request/outcome, then
source/destination/reason plus waiting-to-ready and the next explicit advance.
Equivalent historical retries return their receipt and current status without
activity. Explicit resolve prints an unchanged cursor and a run-status decision
only after saving. Retry may repeat external effects and executes nothing itself.
Inspection and repeated waiting/terminal advance never replay activity.

Final stdout summaries prioritize identity, explained status, cursor, overall
result, transition count, last outcome and next action; source/root/log selectors
follow as secondary detail. Failed status exits 0 and keeps its cause on stderr.
State/completion/I/O errors retain stable codes and add text-only next actions.
Both redirected streams remain independently intelligible; only stderr activity
has an ordered path, with no total ordering promise across streams. At most three
lines accompany a process-result write, one an activation/waiting/end/resolution
write, and two an accepted completion. Existing bounds and synchronous flushing
remain; a closed activity pipe still cannot fail saved work.

This intentionally changes human text; parsers must use explicit --json. Keep
protocol 1, the response types/serializer and one response without human activity.
There is no protocol migration or state rewrite for P20, and no new dependency.
The structured resource identities introduced by P19 remain unchanged. See
[the walkthrough](../FLOW-OUTPUT.md) for representative before/after transcripts.
