# P21 optional start and first advance

Expose `merstride start <file> --advance`. The flag is explicit and discoverable
beside start's existing workspace/workflow/input options; ordinary start remains
ready and nonexecuting. One first advance retains the existing synchronous chain,
agent handoff, terminal/error and limit semantics. Completion still moves only
the cursor. Two native invocations become one without a caller-side wrapper.
This establishes an invocation saving, not measured context/token savings.

Keep preparation and creation in the CLI start module and reuse the same advance
adapter as the separate command. After saving creation and context, release the
root lock and acquire/read only the exact created ID under its writer lock.
Changing current/source selections cannot redirect execution. No engine, process
runner, persisted state, identity, retention or dependency policy changes.

Register cancellation before combined preparation. Before entering creation,
observed cancellation creates nothing. Once creation begins, finish its durable
creation/selection attempt. Check cancellation before acquiring the advance lock;
if observed, retain ready, report INTERRUPTED/130 and no initial advance. This
ready run can be advanced explicitly without resolve. After that check ordinary
advance cancellation applies; even a signal before the first activation can
require explicit resolution. Forced loss of the writer retains ordinary recovery
semantics and may not return output. No atomicity across state and external effects.

Creation, selection and advance are separate phases. Failed creation executes
nothing. Failed selection never advances and retains the new ready identity.
Operational advance errors preserve the identity and durable effects/progress;
fresh status is returned when readable, otherwise status is unknown/null. Existing
error codes/exits and interruption save-failure semantics apply. Never retry,
erase, roll back or infer a different run. Recovery uses exact identity and root.

Protocol 1 gains `start`, null outside handled combined start, or an object with
`created`, `phase` and `advance`. See the contract for its enumerations and the
distinction between normal engine return (`finished`, including workflow failure)
and operational exception (`error`). Keep one stdout JSON object, with no human
activity or concatenated responses. This additive response field requires strict
client allowlists to be updated; no protocol bump or state rewrite is needed.
Argument/project-discovery errors precede the handler and have null metadata.

Human stdout separately reports saved creation and initial progression before
the resulting status and next action. Stderr adds one bounded saved-creation line,
followed by P20's save-linked activity. A closed activity pipe cannot fail saved
work. Creation wording does not imply successful context selection or execution.

Public native CLI scenarios compare separate/combined effects and stopping
conditions, explicit selection/input/workspace, process chains, agents/end nodes,
limits, preparation errors, lock/save failures, concurrent context changes and
real interruption/recovery. Existing architecture/policy tests retain the public
build boundary. No private fault hook or new dependency is introduced. The narrow
creation-to-advance signal window is defined, but controlled native signal tests
exercise interruption during a running attached tree; precise sub-write timing
and physical disk failures are not qualified. Platform/release evidence remains
separate in STATUS.md.
